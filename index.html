业务背景

负责为快递公司搭建 AI 语音助手，主要承担两类业务：快递通知（主动拨出，告知货物到达，预约取件/收货时间）和投诉申诉客服（被动接入，全流程推动用户完成投诉）。

系统基于大语言模型 + ASR 语音识别构建，Prompt 是控制模型行为的核心手段。参与完成多个客户项目的 Prompt 撰写、版本管理与持续调优，累计迭代 20+ 版次。

问题诊断 — 三类核心 Badcase

Badcase 01 · 时间理解偏差

AI 无法识别「货物到达前」的相对时间表达

货物预计到达时间为 5月20日 21:00，当用户说「下午三点来取」时，AI 直接确认了该时间，未触发「抱歉，该时间货物尚未到达」的拒绝话术。

根因：Prompt 中仅定义了绝对时间格式（HH:MM），未涵盖相对时间语义及其与到达时间的大小比较逻辑。「今天下午」「明天上午」「下个工作日」等均未建立映射规则。

Badcase 02 · 情绪用户对话打转

遇到情绪激动用户时，AI 陷入反复循环无法推进

当用户因快递问题情绪激动、重复抱怨或拒绝正面回答时，AI 不断重复同一句安抚话术，形成死循环，无法推动流程进入下一步或主动触发兜底转人工。

根因：Prompt 中安抚逻辑与流程推进逻辑是平行关系，缺少「连续N次未获有效输入→升级兜底」的计数与跳转机制。

Badcase 03 · 环境噪音误识别

将环境人声误判为用户指令，触发错误流程分支

用户接听时旁边有他人说话（如「你先接着，我去拿快递」），ASR 将环境声识别为用户输入，导致 AI 错误执行了"确认收货时间"操作。

根因：Prompt 未设计针对低置信度输入或语义歧义输入的校验机制，对所有 ASR 输出一视同仁。

优化方案

方案 01 · 时间语义扩展定义

为所有相对时间表达建立枚举映射 + Few-shot 示例

在 Prompt 中新增「时间理解规则」模块，穷举用户可能使用的时间表达类型，并为每种类型定义与货物到达时间的比较逻辑，触发对应话术。

Prompt 片段示例（脱敏处理）
【时间理解规则】
货物预计到达时间 = {arrival_time}

用户时间表达分类与处理逻辑：

# 类型A：今日相对时间
"今天上午/下午/晚上" → 转换为当日具体时段
  若转换后时间 < arrival_time → 触发【时间过早话术】
  示例："今天下午三点" 当 arrival 为今晚9点 → 拒绝

# 类型B：明日及以后
"明天" / "后天" / "下个工作日" → 默认可选时间，正常确认

# 类型C：模糊时间
"随时" / "你们定" / "无所谓" → 触发【推荐时间话术】
  主动给出2个可选时间段供用户选择
方案 02 · 情绪计数 + 分级兜底机制

引入连续无效轮次计数，阶梯式升级处理策略

在系统变量中新增「无效轮次计数器」，每次用户输入未能推进流程时累加，达到阈值后自动跳转兜底话术并结束循环，避免无限打转。

兜底触发逻辑（伪代码）
invalid_count = 0  # 无效轮次计数

# 每轮对话结束后判断
IF 本轮未推进流程节点:
    invalid_count += 1

IF invalid_count == 2:
    → 切换安抚话术风格（更简洁直接）
IF invalid_count >= 3:
    → 触发兜底话术：
      "感谢您的耐心，我为您转接人工客服处理"
    → 结束 AI 对话流程
方案 03 · 低置信度输入过滤

设置语义置信度门槛，歧义输入触发二次确认

针对 ASR 识别结果，在 Prompt 中增加输入有效性校验层：若识别内容语义完整度低（过短、与上下文强不相关、含明显环境噪音特征词），则不直接执行指令，先触发确认话术。

输入校验规则示例
【输入有效性判断】

触发「请再说一遍」话术的条件（满足任一）：
  1. 识别文本长度 < 2字 且 不含时间/是/否等关键词
  2. 识别内容与当前对话节点语义不相关
     示例：当前节点=确认时间，识别到"他去拿快递" → 无效
  3. 连续识别到第三人称代词（他/她/你们）
     → 可能为环境人声，触发确认：
       "您好，请问是您在和我说话吗？"

思考与收获

这个项目让我深刻理解了 Prompt 工程的本质：它不只是写指令，而是在自然语言层面定义系统的边界条件和异常处理逻辑。越接近真实用户场景，边界情况就越多，越需要像工程师写防御性代码一样，在 Prompt 中预埋完整的分支覆盖。

语言学背景让我在分析用户时间表达的歧义性时有天然优势——知道「下午」「今天」这类时间词是相对锚定的，需要上下文才能解析绝对值，从而设计出更鲁棒的规则。

分析背景与方法

作为 Claude、ChatGPT、豆包、DeepSeek 的重度用户，我在日常工作、学术与生活场景中持续交叉使用以上产品超过6个月。本报告从产品定位、核心能力、用户体验、差异化策略四个维度展开，结合真实使用场景对豆包进行深度拆解，并提出产品机会点。

核心发现 · 定位差异

竞品定位图谱

四款产品形成了清晰的定位分层

经过长期交叉使用，我观察到四款产品在用户心智中形成了明显的使用场景分工：

豆包核心优势拆解

优势 01 · 语言风格

最接地气的中文表达，真实建立「伙伴感」

豆包的回答风格明显区别于其他产品的「助手腔」——语气自然、口语化，更像是朋友在聊天而非工具在回复。这种风格在生活场景（问天气穿搭、推荐餐厅、聊日常疑惑）中极大降低了用户的心理距离，提升了持续使用的意愿。

产品逻辑：字节系产品深谙内容消费心理，将「信息流亲切感」的设计语言迁移到了对话AI上，这是其他产品难以快速复制的基因优势。

优势 02 · 多模态能力

识图+生图的多模态矩阵，覆盖日常视觉需求

豆包的多模态能力在国产AI产品中属于第一梯队，识图理解能力在日常场景（识别菜品、解析截图、理解图表）中表现稳定，生图功能也能满足基础需求。对于非专业用户，这个能力组合已经足够日用。

横向对比：生图质量与 Claude、ChatGPT（DALL·E）相比仍有差距，精细度和美学表现明显逊色，但免费策略使其在用量上取得优势。

优势 03 · 免费策略

零门槛获客，构建高频使用习惯

完全免费是豆包最强的增长武器。对于高频但低复杂度的生活场景查询，用户不会为此付费——豆包恰好覆盖了这个「值得问但不值得付钱问」的需求区间，形成了差异化的用户分层。

豆包核心问题拆解

问题 01 · 幻觉率偏高

事实性错误出现频率高于竞品，可信度存疑

在实际使用中，豆包出现幻觉（生成错误事实信息）的频率明显高于 Claude 和 ChatGPT。在涉及具体数据、人名、日期等事实性查询时，需要额外验证。这直接限制了豆包在学术和工作场景的可用性。

影响：用户形成「豆包说的要再查一遍」的认知，降低了在高可信度场景的使用意愿，强化了「只用于生活琐事」的用户心智。

问题 02 · 过度顺从，缺乏辩证性

倾向于顺着用户说，而非提供独立批判视角

豆包存在明显的「顺着用户话茬走」的倾向——当用户的前提预设存在问题时，豆包往往不会指出，而是在错误前提下继续作答。相比之下，Claude 会主动标注假设的不确定性并提供反向论据。

根因推测：可能与偏向用户满意度的 RLHF 训练策略有关——「用户觉得舒服」的回答在反馈中得到更高奖励，导致模型系统性地规避对用户的纠正。

问题 03 · 深度写作能力不足

口语化风格是双刃剑，在复杂表达场景中成为劣势

豆包的口语化风格在生活场景是优势，但在需要严密论证、结构化输出的写作任务（学术报告、产品分析、方案文档）中，表现明显弱于 Claude。内容深度、逻辑层次和语言精准度都有差距。

产品机会点

①
引入「可信度标注」机制
对模型置信度较低的事实性内容主动标注「建议验证」，降低幻觉带来的信任损耗，提升用户在专业场景的使用意愿。
②
设计「场景切换」模式
在「生活闲聊模式」之外，提供「深度思考模式」——切换后回答风格更严谨、会主动质疑前提，覆盖用户偶发的工作/学术需求而不破坏日常体验。
③
强化生图质量，缩小与一线产品的差距
当前生图质量是豆包多模态体验的短板。提升美学精细度和提示词理解能力，将「能用」升级为「好用」，进一步巩固多模态日常场景的护城河。

结论

豆包的成功在于找到了一个竞争对手尚未充分占据的心智位置：中文互联网用户日常生活中的轻量 AI 伙伴。免费策略 + 亲切语言风格 + 多模态能力，构成了差异化的产品组合。

然而，过度顺从和幻觉问题形成了一道隐形的天花板——用户信任豆包处理「无所谓对不对」的生活问题，却不敢用它处理「必须准确」的工作问题。如何在保留「伙伴感」的同时提升可信度，是豆包破圈的核心命题。

需求来源 · 真实痛点

需求洞察

数据标注员的「黑盒感」——做了贡献，却看不见结果

在参与字节跳动大模型数据标注项目时，我完成了大量语料标注工作，但始终无法得知：这批数据被哪个版本的实验使用了？标注质量对模型效果有多大影响？哪类数据对训练效果提升最显著？

这种「数据→训练→结果」的断层，不只影响标注员的参与感，更让算法工程师难以追溯实验效果与数据质量之间的关系——当模型表现下降时，无法快速定位是数据问题还是算法问题。

问题定义

痛点 01 · 数据侧

标注数据与训练实验之间缺乏可见的关联关系

标注员完成数据交付后，无法得知数据流向与使用状态；算法工程师启动训练时，也难以快速检索「哪批数据曾用于类似实验」，造成数据资产的重复生产与浪费。

痛点 02 · 实验侧

多实验并行时，实验配置与结果难以系统性管理

ML工程师同时跑多个训练实验时，依赖本地文档或口头约定记录实验参数、数据版本和指标结果，缺乏统一的实验管理入口，导致经验无法沉淀、复盘困难。

痛点 03 · 协作侧

数据团队与算法团队之间信息不透明，协作成本高

数据团队不了解模型训练的优先级变化，算法团队也无法实时感知数据供给状态，双方需要通过大量沟通对齐进度，协作效率低下。

功能设计 · 核心模块

模块 01 · 实验档案卡

每个训练实验自动生成结构化档案，记录完整上下文

工程师发起训练任务时，系统自动关联并记录：所用数据集版本、数据量与质量分布、关键超参数配置、训练结果指标（Loss / Accuracy / 业务指标）。档案卡支持手动补充备注与标签，实验经验可沉淀复用。

用户故事
作为 ML 工程师，
我希望在发起新实验时，能直接搜索并引用
历史相似实验的数据配置，
以便复用已验证的数据方案，减少重复探索成本。

验收标准：
✓ 搜索结果支持按数据集版本、任务类型、时间筛选
✓ 引用历史配置时，系统自动提示版本差异
✓ 引用操作 3 步以内完成
模块 02 · 数据流向追踪

标注数据从产出到使用的全链路可视化

每批标注数据完成交付后，系统自动追踪其被哪些实验引用、在各实验中的使用比例，以及关联实验的最终效果指标。标注员可在个人工作台查看自己数据的"流向图"，算法团队可反向定位"哪批数据对效果贡献最大"。

用户故事
作为数据标注员，
我希望在完成一批标注任务后，
能看到这批数据被哪个实验版本使用，
以便了解自己的贡献，并根据模型反馈
持续改进标注质量。

验收标准：
✓ 数据状态：待使用 / 训练中 / 已完成 实时可见
✓ 关联实验的核心指标对标注员可见（脱敏处理）
✓ 质量评分变化趋势图可查看
模块 03 · 实验对比看板

多实验横向对比，快速定位效果差异的数据归因

研究员可选择多个实验版本进行并排对比，系统高亮展示数据配置差异与指标差异的关联关系，辅助判断效果波动是否由数据质量或数据分布变化引起。

用户故事
作为算法研究员，
我希望在模型指标下降时，
能快速对比本次实验与上次实验的数据差异，
以便在1小时内判断是数据问题还是算法问题，
而非花2天逐一排查。

验收标准：
✓ 支持最多 4 个实验并排对比
✓ 数据差异自动高亮（新增 / 删除 / 比例变化）
✓ 支持导出对比报告为 PDF

范围说明 · 本期不做什么

本期 不包含：模型训练本身的调度功能（属于训练平台核心能力，另立项）、数据标注工具的改造（属于标注平台范畴）、面向外部企业客户的开放 API（属于商业化阶段规划）。聚焦在「数据与实验的关联追踪和可见性」这一核心场景，避免范围蔓延。

设计反思

这篇 PRD 的需求来源于我在大模型数据标注岗位的真实体验——作为数据生产者，却对数据的去向和价值一无所知。这种「黑盒感」不仅影响标注积极性，更是 ML 平台效率提升的隐性障碍。

在功能设计上，我刻意把「标注员」列为次要用户，将其流向追踪功能纳入 P1 优先级，而非边缘化处理——因为数据生产侧的正向反馈机制，是保障数据质量持续优化的关键杠杆，这往往是纯工程视角容易忽视的部分。

产品定位

Recall 是一款面向知识工作者和内容消费者的AI 内容收藏工具。用户粘贴任意网页链接，AI 自动抓取、分析、总结内容，生成标题、摘要、分类和标签，一键收藏到个人知识库中。

核心差异化在于「AI 自动分类 + 用户自定义管理」的双轨制：AI 智能分析确保低摩擦入库，用户可随时修改分类、标签，确保知识库始终贴合个人认知体系。

功能亮点

亮点 01 · AI 智能分析

链接粘贴 → AI 分析 → 一键收藏，三步完成

基于 DeepSeek API 自研分析 Pipeline：网页抓取 → 正文提取 → 结构化分析（标题 / 摘要 / 分类 / 标签）。支持中英文混合内容，摘要控制在 80 字以内。

亮点 02 · 多用户隔离

基于 Supabase Auth 的完整用户体系，数据完全隔离

JWT 鉴权中间件 + 数据库行级过滤，确保每个用户只能看到自己的收藏内容。支持快速保存接口（iOS Share Extension 场景）。

亮点 03 · 用户自定义分类

每用户独立管理分类标签，云端同步跨设备

支持增删改分类标签，后端存储 + 前端缓存的双层架构。内置「Other」分类自动收纳未匹配内容，用户可随时手动调整内容归属。

亮点 04 · 交互打磨

阅读状态追踪、定时提醒、回收站、2秒撤销删除

已读/未读状态管理，基于创建时间的 3天/7天/30天 分级提醒标签。删除操作带 2 秒倒计时撤销机制，回收站 3 天自动清理。

关键设计决策

决策 01 · 前端分类 vs 后端分类

从 localStorage 演进到后端存储

初版将分类标签存储在浏览器 localStorage 中，快速上线但发现两个问题：不同设备不同步、同一浏览器多账号共享标签。二版重构为 Supabase 存储 + API 驱动，实现真正的按用户隔离和跨设备同步。

决策 02 · AI 分析架构

预览-确认两阶段模式，降低 AI 调用浪费

AI 分析返回预览结果，用户确认后才写入数据库。避免用户对分析结果不满意时产生冗余写入，同时允许用户在确认前修改分类、标题等内容。

项目反思

这个项目是我在 Vibe Coding 范式下的完整实践：利用 Claude Code 等 AI 编程工具，从需求定义、技术选型、前后端开发到部署运维，一个人完成全部环节。

最大的体悟是：AI 辅助编程的核心不是「让 AI 写代码」，而是「产品思维 + 工程判断 + AI 执行」的三位一体。AI 可以快速生成大量代码，但架构决策（如分类存储从 localStorage 到后端的演进）、用户体验打磨（如 2 秒撤销倒计时）、以及安全性设计（如 JWT 鉴权 + 行级过滤），仍然需要人的产品判断和工程经验来驱动。
