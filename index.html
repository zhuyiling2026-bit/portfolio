业务背景

负责为快递公司搭建 AI 语音助手，主要承担两类业务：快递通知（主动拨出，告知货物到达，预约取件/收货时间）和投诉申诉客服（被动接入，全流程推动用户完成投诉）。

系统基于大语言模型 + ASR 语音识别构建，Prompt 是控制模型行为的核心手段。参与完成多个客户项目的 Prompt 撰写、版本管理与持续调优，累计迭代 20+ 版次。

问题诊断 — 三类核心 Badcase

Badcase 01 · 时间理解偏差

AI 无法识别「货物到达前」的相对时间表达

货物预计到达时间为 5月20日 21:00，当用户说「下午三点来取」时，AI 直接确认了该时间，未触发「抱歉，该时间货物尚未到达」的拒绝话术。

根因：Prompt 中仅定义了绝对时间格式（HH:MM），未涵盖相对时间语义及其与到达时间的大小比较逻辑。「今天下午」「明天上午」「下个工作日」等均未建立映射规则。

Badcase 02 · 情绪用户对话打转

遇到情绪激动用户时，AI 陷入反复循环无法推进

当用户因快递问题情绪激动、重复抱怨或拒绝正面回答时，AI 不断重复同一句安抚话术，形成死循环，无法推动流程进入下一步或主动触发兜底转人工。

根因：Prompt 中安抚逻辑与流程推进逻辑是平行关系，缺少「连续N次未获有效输入→升级兜底」的计数与跳转机制。

Badcase 03 · 环境噪音误识别

将环境人声误判为用户指令，触发错误流程分支

用户接听时旁边有他人说话（如「你先接着，我去拿快递」），ASR 将环境声识别为用户输入，导致 AI 错误执行了"确认收货时间"操作。

根因：Prompt 未设计针对低置信度输入或语义歧义输入的校验机制，对所有 ASR 输出一视同仁。

优化方案

方案 01 · 时间语义扩展定义

为所有相对时间表达建立枚举映射 + Few-shot 示例

在 Prompt 中新增「时间理解规则」模块，穷举用户可能使用的时间表达类型，并为每种类型定义与货物到达时间的比较逻辑，触发对应话术。

Prompt 片段示例（脱敏处理）
【时间理解规则】
货物预计到达时间 = {arrival_time}

用户时间表达分类与处理逻辑：

# 类型A：今日相对时间
"今天上午/下午/晚上" → 转换为当日具体时段
  若转换后时间 < arrival_time → 触发【时间过早话术】
  示例："今天下午三点" 当 arrival 为今晚9点 → 拒绝

# 类型B：明日及以后
"明天" / "后天" / "下个工作日" → 默认可选时间，正常确认

# 类型C：模糊时间
"随时" / "你们定" / "无所谓" → 触发【推荐时间话术】
  主动给出2个可选时间段供用户选择
方案 02 · 情绪计数 + 分级兜底机制

引入连续无效轮次计数，阶梯式升级处理策略

在系统变量中新增「无效轮次计数器」，每次用户输入未能推进流程时累加，达到阈值后自动跳转兜底话术并结束循环，避免无限打转。

兜底触发逻辑（伪代码）
invalid_count = 0  # 无效轮次计数

# 每轮对话结束后判断
IF 本轮未推进流程节点:
    invalid_count += 1

IF invalid_count == 2:
    → 切换安抚话术风格（更简洁直接）
IF invalid_count >= 3:
    → 触发兜底话术：
      "感谢您的耐心，我为您转接人工客服处理"
    → 结束 AI 对话流程
方案 03 · 低置信度输入过滤

设置语义置信度门槛，歧义输入触发二次确认

针对 ASR 识别结果，在 Prompt 中增加输入有效性校验层：若识别内容语义完整度低（过短、与上下文强不相关、含明显环境噪音特征词），则不直接执行指令，先触发确认话术。

输入校验规则示例
【输入有效性判断】

触发「请再说一遍」话术的条件（满足任一）：
  1. 识别文本长度 < 2字 且 不含时间/是/否等关键词
  2. 识别内容与当前对话节点语义不相关
     示例：当前节点=确认时间，识别到"他去拿快递" → 无效
  3. 连续识别到第三人称代词（他/她/你们）
     → 可能为环境人声，触发确认：
       "您好，请问是您在和我说话吗？"

思考与收获

这个项目让我深刻理解了 Prompt 工程的本质：它不只是写指令，而是在自然语言层面定义系统的边界条件和异常处理逻辑。越接近真实用户场景，边界情况就越多，越需要像工程师写防御性代码一样，在 Prompt 中预埋完整的分支覆盖。

语言学背景让我在分析用户时间表达的歧义性时有天然优势——知道「下午」「今天」这类时间词是相对锚定的，需要上下文才能解析绝对值，从而设计出更鲁棒的规则。

分析背景与方法

作为 Claude、ChatGPT、豆包、DeepSeek 的重度用户，我在日常工作、学术与生活场景中持续交叉使用以上产品超过6个月。本报告从产品定位、核心能力、用户体验、差异化策略四个维度展开，结合真实使用场景对豆包进行深度拆解，并提出产品机会点。

核心发现 · 定位差异

竞品定位图谱

四款产品形成了清晰的定位分层

豆包核心优势拆解

优势 01 · 语言风格

最接地气的中文表达，真实建立「伙伴感」

豆包的回答风格明显区别于其他产品的「助手腔」——语气自然、口语化，更像是朋友在聊天而非工具在回复。这种风格在生活场景（问天气穿搭、推荐餐厅、聊日常疑惑）中极大降低了用户的心理距离，提升了持续使用的意愿。

产品逻辑：字节系产品深谙内容消费心理，将「信息流亲切感」的设计语言迁移到了对话AI上，这是其他产品难以快速复制的基因优势。

优势 02 · 多模态能力

识图+生图的多模态矩阵，覆盖日常视觉需求

豆包的多模态能力在国产AI产品中属于第一梯队，识图理解能力在日常场景（识别菜品、解析截图、理解图表）中表现稳定，生图功能也能满足基础需求。对于非专业用户，这个能力组合已经足够日用。

横向对比：生图质量与 Claude、ChatGPT（DALL·E）相比仍有差距，精细度和美学表现明显逊色，但免费策略使其在用量上取得优势。

优势 03 · 免费策略

零门槛获客，构建高频使用习惯

完全免费是豆包最强的增长武器。对于高频但低复杂度的生活场景查询，用户不会为此付费——豆包恰好覆盖了这个「值得问但不值得付钱问」的需求区间，形成了差异化的用户分层。

豆包核心问题拆解

问题 01 · 幻觉率偏高

事实性错误出现频率高于竞品，可信度存疑

在实际使用中，豆包出现幻觉（生成错误事实信息）的频率明显高于 Claude 和 ChatGPT。在涉及具体数据、人名、日期等事实性查询时，需要额外验证。这直接限制了豆包在学术和工作场景的可用性。

影响：用户形成「豆包说的要再查一遍」的认知，降低了在高可信度场景的使用意愿，强化了「只用于生活琐事」的用户心智。

问题 02 · 过度顺从，缺乏辩证性

倾向于顺着用户说，而非提供独立批判视角

豆包存在明显的「顺着用户话茬走」的倾向——当用户的前提预设存在问题时，豆包往往不会指出，而是在错误前提下继续作答。相比之下，Claude 会主动标注假设的不确定性并提供反向论据。

根因推测：可能与偏向用户满意度的 RLHF 训练策略有关——「用户觉得舒服」的回答在反馈中得到更高奖励，导致模型系统性地规避对用户的纠正。

问题 03 · 深度写作能力不足

口语化风格是双刃剑，在复杂表达场景中成为劣势

豆包的口语化风格在生活场景是优势，但在需要严密论证、结构化输出的写作任务（学术报告、产品分析、方案文档）中，表现明显弱于 Claude。内容深度、逻辑层次和语言精准度都有差距。

产品机会点

①
引入「可信度标注」机制
对模型置信度较低的事实性内容主动标注「建议验证」，降低幻觉带来的信任损耗，提升用户在专业场景的使用意愿。
②
设计「场景切换」模式
在「生活闲聊模式」之外，提供「深度思考模式」——切换后回答风格更严谨、会主动质疑前提，覆盖用户偶发的工作/学术需求而不破坏日常体验。
③
强化生图质量，缩小与一线产品的差距
当前生图质量是豆包多模态体验的短板。提升美学精细度和提示词理解能力，将「能用」升级为「好用」，进一步巩固多模态日常场景的护城河。

结论

豆包的成功在于找到了一个竞争对手尚未充分占据的心智位置：中文互联网用户日常生活中的轻量 AI 伙伴。免费策略 + 亲切语言风格 + 多模态能力，构成了差异化的产品组合。

然而，过度顺从和幻觉问题形成了一道隐形的天花板——用户信任豆包处理「无所谓对不对」的生活问题，却不敢用它处理「必须准确」的工作问题。如何在保留「伙伴感」的同时提升可信度，是豆包破圈的核心命题。
